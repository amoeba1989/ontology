# 04 · 对照知彼的差距

逐维度对比，结论只服务于一个问题：**改造预算应该花在哪**。

打分口径：`0` 没有；`1` 有零散实现/手工流程；`2` 有一等公民的数据结构与接口；`3` 默认路径上自动生效且有门禁。

## 三条结构性判断

**1. 我们最大的差距不在产品功能，而在门禁的覆盖面。**
Semantica 的产品承诺有一半是虚的，但它的 CI 是实的。知彼这边测试确实在 GitHub Actions 里跑，问题是**跑的是一份点好的名单**（5/11），且办公室日常推送的 Gitee Go 流水线**完全跳过测试**。结果就是：改坏一个没在名单里的行为，部署照样成功，而且没人会知道。这比"缺 SHACL"严重得多，因为它会持续制造新债务。

**2. 溯源/解释/决策留痕是同一件事的三个切面，应该一起设计。**
它们都要求同一个底层能力：**每条结论知道自己来自哪里**。知彼已经有 `ConditionResult`（规则）和 `AgentTrace`（执行）两个半成品，缺的是把它们收敛成一个"证据"概念。分开补会返工。

**3. 我们的领先维度要守住，不要被"开源项目功能清单"带偏。**
连接器框架、发布流水线、G6 双层画布、场景注册与 RBAC 是 Semantica 完全没有的，也是客户付钱的原因。改造投入应该只从它的**知识工程方法论**和**工程纪律**里取，不碰它的平台形态。

## 一句话优先级

先补 CI 门禁（不改动产品代码，风险为零）→ 抽取出处回指（几十行，演示效果立竿见影）→ 规则解释链（地基已有）→ 溯源数据结构（一次设计到位，避免做成第二个 `AgentTrace`）。

具体动手顺序、要改的文件和验收标准见 [05-改造路线.md](05-改造路线.md)。
