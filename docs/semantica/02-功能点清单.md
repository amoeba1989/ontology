# 02 · 功能点清单

按模块列出 Semantica 实际实现了什么、代码在哪、对我们有没有参考价值。「抄度」列的含义：

- **照抄** — 数据结构或流程逻辑可以直接移植，改动量小
- **改造** — 思路对，但要按知彼的平台形态重写
- **不抄** — 它自己的实现就不完整，或与我们定位无关

## 1. 本体管理（`semantica/ontology/`）

| 功能点 | 证据 | 说明 | 抄度 |
|---|---|---|---|
| 草案本体自动归纳 | `ontology/` 六阶段生成链 | 从已抽取的三元组反向归纳出类/属性/域名范围，先生成"草案"再人工确认，而非一上来就要求用户建模 | 改造 |
| 产物格式 | 生成 TTL / OWL 序列化 | 与 `rdflib` 对接，标准 W3C 语法落地 | 照抄 |
| SHACL 形状约束 | 基于 `pyshacl` | 用数据形状（SHACL Shape）声明"某类必须有 N 个某属性、值域必须符合 X"，实例数据入图前跑一遍校验 | **照抄** |
| 版本化 IRI | 版本随 IRI 命名空间走 | 每个本体版本有独立可寻址 IRI，旧版本可原地查询 | 改造 |
| 版本 diff / migrate | diff 生成 + 迁移脚本 | 对比两版差异，并对实例数据给出迁移建议 | **照抄** |
| OWL DL 一致性推理 | `ontology_validator.py:336-353` | **占位实现**，实际是启发式检查，不是 HermiT/Pellet 级描述逻辑推理 | 不抄 |

对我们最有价值的是 SHACL 那两行：知彼现在约束本体的是 `backend/app/services/ontology_constraints.py`（126 行），里面主要是 **prompt 里的命名规范 + tier 判定树 + pydantic `OntologyOutput` 结构校验**。它管的是"AI 抽取出来的东西格式对不对"，不管"实例数据符不符合本体声明"。SHACL 正好补的是后半段。

## 2. 知识抽取管线（`semantica/extraction/`、`semantica/graph/`）

| 功能点 | 规模 | 说明 | 抄度 |
|---|---|---|---|
| 文档解析器 | 23 种 | 格式覆盖广，但对我们只是"多支持几种文件" | 不抄 |
| 切块策略 | 6 种（含滑窗） | 滑窗切块刚在 `#1920` 修过，说明这块在持续演进 | 改造 |
| LLM Provider 适配 | 8 家 | 知彼走 OpenAI 兼容协议单一入口，不需要 8 家适配 | 不抄 |
| **防幻觉 span 校验** | `_find_span_in_text` | 抽取出的实体/关系必须回填到原文片段，回找不到就丢弃。这是**代价最低、收益最高的一条约束** | **照抄** |
| 抽取门控 | draft → approve → `filter_by_schema` | 草案先落库，审批后才允许写主图，中间有一层 schema 过滤 | **照抄** |

## 3. 实体消歧与冲突裁决（`semantica/dedup/`、`conflict/`）

| 功能点 | 说明 | 抄度 |
|---|---|---|
| 三层去重 | 精确 → 模糊（Jaro-Winkler / Levenshtein）→ 语音（Soundex），逐层放宽、逐层加速 | 照抄 |
| 冲突分类 | 5 类冲突（类型/属性值/基数/关系方向/等价） | 照抄 |
| 裁决策略 | 6 种策略（最新优先、来源优先级、投票、人工升级等），策略可按冲突类型配置 | 照抄 |
| 与信任级联动 | 裁决时读 `TrustTier`，高信任来源覆盖低信任来源 | 改造 |

知彼侧对应的是 `backend/app/api/v1/resolution.py`（270 行），但它做的是**「映射后的源数据 → 本体实体实例」的解析**，不是同名实体归一。也就是说"同一个客户在三张表里叫三个名字"这件事，我们目前没有系统性处理。

## 4. 推理（`semantica/reasoning/`）

| 功能点 | 说明 | 抄度 |
|---|---|---|
| 规则引擎 | 含 **RETE 网络**，规则多时不逐条重算 | 改造 |
| Datalog / SPARQL / 溯因 | 多种查询与推理范式并存 | 不抄（选一个即可） |
| `InferenceResult` | 每次派生结果是**结构化对象**：结论 + 命中的规则 + 代入的值 + 时间戳 | **照抄** |
| `ExplanationGenerator` | 把 `InferenceResult` 渲染成人类可读的推理路径 | **照抄** |
| 真值维护 TMS | `FactSupport` 记录每条事实依赖哪些前提；前提撤销时自动失效派生事实 | **照抄** |
| 因果推理 | README 口径，实为决策图遍历 | 不抄 |

知彼有 `backend/app/services/rule_engine.py`（701 行），`ConditionResult` 已经是结构化结果 —— 我们的地基其实不差，缺的是**"为什么得出这个结论"的证据链输出**和**事实依赖失效**。

## 5. 溯源（`semantica/provenance/`）

| 功能点 | 说明 | 抄度 |
|---|---|---|
| `ProvenanceEntry` | 对齐 **W3C PROV-O** 的实体/活动/代理三元组 | 照抄 |
| 哈希链 | `verify_chain()` 顺序校验，任何一条被改动都能检测出来 | **照抄** |
| 墓碑删除 | `invalidate()` 不物理删，写一条"作废声明"，历史仍可重建 | **照抄** |
| 实际接线 | ⚠ 三个 `*_provenance.py` 里的 import 是死代码；溯源管理器只在 `cli.py` 和 `explorer/session.py` 被调用，**默认抽取管线不写溯源** | 不抄它的实现，抄它的设计 |

这一条要特别注意：它证明了"数据结构设计得很好"和"真的接通了"是两件事，我们照抄时必须连接线一起抄，否则又做一个装饰品。

## 6. 决策与上下文（`semantica/decision/`、`context/`）

| 功能点 | 说明 | 抄度 |
|---|---|---|
| Context Graph | 把"某次任务需要哪些上下文"图化存储 | 改造 |
| `Decision` / `Precedent` | 决策记录 + 判例引用，可查"上次类似情况怎么判的" | **照抄** |
| `Policy` / `PolicyException` | 策略与策略豁免分离建模，豁免本身留痕 | 照抄 |
| `ApprovalChain` | ⚠ 只是单条审批流水记录，不是编排引擎 | 不抄 |
| `TrustTier` | 来源信任分级，参与裁决与展示 | 照抄 |

知彼侧最接近的是 `models/trace.py` + `AgentTrace`（执行追踪），但那是**过程留痕**，不是**决策留痕** —— 记的是"Agent 调了哪些工具、花多少 token"，不记"这个业务结论依据哪条规则、哪些事实、什么时间的数据"。

## 7. 评测（`semantica/evals/`）

| 功能点 | 说明 | 抄度 |
|---|---|---|
| `stable_pass` / `flaky` / `stable_fail` 三态 | 不把偶发失败的测试直接删掉或改成永远通过，而是显式标记成 flaky 并持续观察 | **照抄** |
| 预期输出对比 | 批量评测集 + 指标追踪 | 改造（知彼已有 `models/eval.py`） |

## 8. 服务与集成

| 功能点 | 证据 | 说明 | 抄度 |
|---|---|---|---|
| MCP 服务 | `semantica_mcp/mcp/server.py`，手写 JSON-RPC 2.0 over stdio，18 工具 | ⚠ **无鉴权**、整份 JSON 全量读写磁盘；与包内另一套 MCP 实现重复 | 不抄 |

## 9. 工程纪律（最值得整体搬走的部分）

| 功能点 | 说明 | 抄度 |
|---|---|---|
| 已知失败债务台账 | CI 里维护一份"当前失败清单"，新增失败即红，**修掉一个就必须从台账删一个**，台账本身有大小上限 | **照抄** |
| `docs_check.py` 链接门 | 校验文档内链与相对路径是否存在，防止文档腐烂 | **照抄** |
| GitHub Action SHA 固定 + `verify-action-pins.yml` | 所有第三方 action 按 commit SHA 引用，CI 里再跑一个 job 校验没被改成 tag | **照抄** |
| 依赖哈希/新鲜度 diff 门禁 | lock 文件变化时对比，防止偷偷引入新依赖 | 照抄 |
| CVE 忽略需写可达性论证 | `.gitignore`/扫描配置里每条被忽略的漏洞旁边必须有一段说明 | **照抄** |
| CHANGELOG 444KB、每条带 issue 号与新增测试文件名 | 说明"改了什么都必须能查到" | 改造 |
| Dockerfile：digest 锁基础镜像、运行时卸 pip、逐条 CVE 注释 | 见 `01` | 改造 |

## 10. 数据接入（`semantica/ingest/`、`semantica/parse/`）

> ⚠ 更正：早期版本把这块记成"0–1，靠 `integrations/` 薄层"，**是错的**。`integrations/` 只是给 langchain/crewai 那类外部框架用的适配层，真正的接入代码在 `semantica/ingest/`。

| 功能点 | 证据 | 说明 | 抄度 |
|---|---|---|---|
| 接入器 | `ingest/` **42 个文件**：db / snowflake / bigquery / redshift / databricks / duckdb / cassandra / mongo / elastic / kafka(stream) / s3(cloud) / gdrive / huggingface / repo / email / feed / web / xml / parquet / arrow / pandas / api / public_api / mcp / ontology / tableau / powerbi / looker / salesforce / sap / servicenow / dynamics365 / airflow / screening / ssrf … | 覆盖面极广，SaaS 与 BI 系统都有一层 | 不抄（我们的连接器框架更成体系） |
| 解析器 | `parse/` 23 个（pdf/docx/xlsx/pptx/html/image/media/code/docling/csv/json/email/mcp/structured…） | 文档格式覆盖是真资产 | 按需补 |
| 方法注册表 | `ingest/registry.py`：`method_registry.register(task, method, fn)`，task 维度是 `file/web/feed/stream/repo/email/db/api/public_api/parquet/ingest/screen`，method 维度是 `url/sitemap/crawl/endpoint/batch/schema/metadata/validate…` | **两级 (task, method) 注册 + 运行期动态注册**，比我们的硬编码注册灵活；`list_all()` 供前端建表 | **照抄** |
| 配置三级回落 | `ingest/config.py`：config file(YAML/JSON/TOML) → env(`INGEST_MAX_FILE_SIZE` 等) → 默认值 | 与知彼 pydantic-settings 思路一致 | 不抄 |
| SSRF 防护 | `ingest/ssrf.py`：先 DNS 解析再判 `_ip_is_blocked`，重定向时按需剥离 Authorization | 我们读外部 URL/API 时缺这层 | **照抄** |
| 内容预筛 | `ingest/screening.py`：`baseline_scan(text)` 出 `ScreeningFinding`，**刻意不抄原文摘录**以免把密钥写进报告 | 设计取向值得学 | 照抄 |
| 文件大小/类型校验 | `file_ingestor.py`：扩展名 + MIME + magic number 三重判型，`FILE_SIZE_LIMITS` | — | 参考 |

**但它这条链没闭合**（这是"接入"这块最该记住的事实）：

- `cli.py:2247-2270` 的 `--store` 选项 help 里自己写着 **"Not yet implemented — ingest cannot persist to a graph store"**，配置了 Neo4j/FalkorDB/AGE/Neptune 且没传 `--output` 时**直接报错拒绝假装成功**，对应 issue `#1351`、`#1352`。
- 所以 CLI 侧的闭环只到"导出 `.json/.jsonl/.csv`"，真正入图要在 Python 里手搓 `GraphBuilder`。
- 没有 Connection / Asset 概念：连接串现场传参（`ingest_database("postgresql://user:pass@host/db")`），**凭据不托管、无 schema 快照、无数据画像、无字段契约**。这几点恰恰是知彼 `models/connection.py` + `models/asset.py` 已经解决的问题。
- 默认编排见 `pipeline/pipeline_templates.py` 的 `document_processing`：`ingest → parse → normalize → extract → embed → build_kg`，是**文档管线**，不是数据集成管线。

## 11. 血缘与溯源（`semantica/provenance/`）

它这块叫 provenance（溯源），不叫 lineage —— 但**确实提供 lineage 查询**，两者关系是"血缘 = 溯源图的遍历视图"。详见本节 A/B 两套系统，以及 [03](03-设计亮点与薄弱点.md) 关于"未接默认管线"的警告。

| 功能点 | 证据 | 说明 | 抄度 |
|---|---|---|---|
| 两套并存 | `provenance/manager.py`（PROV-O）与 `conflicts/source_tracker.py`（属性级来源） | `track_property_source(entity, prop, value, source)` 被 `conflict_detector.py`、`methods.py` **真实调用**；PROV-O 那套只被 CLI 与 explorer 调用 | 两套都要，但职责分清 |
| 血缘方向 | `get_lineage()`（BFS 上溯祖先）、`trace_descendants()` / `get_descendants()`（反向下溯） | 下溯是 `issue #825` 才补的；此前 explorer 里 `direction="downstream"` 是**死代码** | 照抄（上+下必须有，否则答不了"这条错了影响谁"） |
| 边的语义 | `parent_entity_id`、`used_entities`、`derived_from_id`、`previous_version_id`、`supersedes` | 都是 PROV-O 关系，不是"表→表" | 改造 |
| 粒度 | `source_document` / `source_location` / `source_quote` / `start_index` / `end_index` | 最小单位是**原文引用**，不是字段 | 这正是与我们血缘的互补点 |
| 完整性 | `checksum` + `previous_checksum` + `sequence_id` 哈希链；`verify_chain()`、`check(strict)` 会检出 `A -> B` 悬空引用 | 篡改可检测 | **照抄** |
| 失效 | `invalidate()` + `invalidated_at_time/by/reason` 墓碑；`revision_history()`、`valid_from/valid_until` | 历史可重建 | **照抄** |
| 存储 | `provenance/storage.py`：`InMemoryStorage` + `SQLiteStorage`（`CREATE TABLE IF NOT EXISTS provenance`，`used_entities/metadata/informed_by_activities` 存 JSON 列） | 单文件 SQLite，与我们的元数据库同构 | 照抄 |
| W3C 导出 | `export_prov(format="turtle")` 生成 `prov:` 三元组（含 `wasDerivedFrom`、`used`） | 可对接外部语义工具 | 参考 |

## 12. 文档组织

`choose-your-module.md` 是一张**意图路由表**：用"你想做什么"而不是"模块叫什么"来索引文档。对小团队降门槛很有效，知彼的 `docs/` 目前是按功能域平铺，新人进来不知道该从哪读。

抄度：**照抄**，成本是半小时。
