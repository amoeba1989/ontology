# 05 · 改造路线

**动手时只看这一篇。** 每条给出：做什么、动哪些文件、怎么验收、多大代价。顺序按「投入产出比」排，不按维度重要性排。

前置约定：

- 知彼的构建与部署都在生产 ECS 上执行（Gitee Go `deploy@agent` / GitHub Actions 同理），所以**任何加进流水线的检查都会直接拉长部署时间** —— 门禁必须能秒级到十几秒跑完，慢的放 UAT。
- 推 `master` 会触发生产部署。改造期间的验证走临时分支或 `deploy` 环境（`compose.uat.yml`，8090）。

## P0 · 先止血：把测试门禁补到「日常推送的那条路」上

现状要说准，不能笼统讲"CI 没跑测试"：

- GitHub Actions（`.github/workflows/deploy.yml`）**有** `verify` job：跑 5 个后端测试文件 + 前端 `vite build`；`deploy` job 还额外要求 `vars.DEPLOY_ENABLED == 'true'`。
- 但 `backend/tests/` 实际有 **11** 个测试文件，CI 里是**点名**跑的 —— 白名单式，新增测试不会自动纳入。剩下 6 个（`test_function_executor`、`test_modeling_drafts`、`test_ontology_mapping`、`test_quality_auto_mount`、`test_rule_function_integration`、`test_copilot_agent_chat`）等于没在跑。
- Gitee Go（`.workflow/流水线-202610131624.yml`）**没有测试 stage**，两个 stage 都是 `deploy@agent`。而办公室网络只能推 Gitee，等于**日常推送走的是无测试那条路**，测试只在能连 GitHub 时才生效。

**做法**

1. 把 GitHub 侧的点名跑法改成目录级：`python -m pytest tests -q --disable-warnings`。第一次很可能有失败用例，用第 3 步的台账兜住，不要为了变绿退回白名单。
2. Gitee Go 侧加一个测试步骤。注意它跑在生产 ECS 上（与构建同机），耗时直接算进部署时间；实测过慢就只跑非集成子集，但**必须是目录级发现，不是文件点名**。
3. 引入「已知失败台账」：`backend/tests/known_failures.txt` 列出当前允许失败的用例 ID。CI 逻辑 = 跑全量 → 与台账做集合差 → **台账外的新增失败即红**；用例已修好却仍留在台账里也报错（提醒删）。这才是把"测试不稳定"从借口变成待办的机制，比多写几个测试有用。
4. **把前端类型检查找回来。** `frontend/package.json` 的 `build` 脚本是 `vue-tsc -b && vite build`，但 Dockerfile 第 15 行和 `.github/workflows/deploy.yml` 第 42 行都直接跑 `pnpm exec vite build` —— **类型检查被绕过了**，坏的 `.vue`/`.ts` 能一路构建成功。改成 `pnpm run build` 即可，代价是一点点构建时间。

**涉及文件**：`.github/workflows/deploy.yml`、`.workflow/流水线-202610131624.yml`、新增 `backend/tests/known_failures.txt`、`frontend/package.json`（复用已有 scripts）

**验收**：故意把一个**不在原名单内**的测试断言改错 → 部署失败；把它加进台账 → 通过；从台账删掉 → 再次失败。

**代价**：半天。风险：测试依赖（DB、模型密钥）导致误红 —— 用台账兜住，不要追求一次全绿。

## P1 · 抽取出处回指（防幻觉，最高性价比的产品改动）

**做法**：LLM 抽取出的每条实体/关系带一个 `source_span` 字段，落库前在原文里做一次精确/模糊定位（先 `in` 匹配，再做去空白与大小写的匹配）；定位失败 → 标记 `unverified` 而不入库主图。

**涉及文件**：`backend/app/services/ontology_constraints.py`（在现有校验链里加一步）、`backend/app/services/doc_builder.py` 与 `ai_builder_v2.py`（把原文文本传进校验）、`backend/app/schemas/ontology_output.py`（加字段）、前端实体详情（展示"第 N 段支撑"）

**验收**：拿演示文档跑一次抽取，人为把某条关系名改成原文不存在的词 → 它被标 `unverified` 且不出现在正式本体里。

**代价**：1–2 天。副作用：抽取召回率会下降，这是**期望结果**，需要在 UI 上把"待确认"数量显示出来，让业务方知道有多少被拦下。

## P2 · 实例对本体约束的校验（SHACL 的简化版）

不必引入 pyshacl。我们本体已经有实体/属性/关系与必填、主键信息，做一次"形状校验器"就够用。

**做法**：新增 `backend/app/services/shape_validator.py`，输入 = 本体版本 + 一批实例，输出 = 违规列表（缺必填、类型不符、基数越界、引用不存在的对象）。把它挂到现有**注水验证**阶段的第 4 步「策略输出」旁边，复用已有的 SSE 进度通道。

**涉及文件**：新增 `services/shape_validator.py`；`app/services/builder/`（注水验证服务）、`app/api/v1/builder.py`；`app/models/quality_rule.py` 的 `RULE_KINDS` 可复用其留痕方式（`HealthStatus` 那套按时间存最新状态的模式很合适）

**验收**：造一条缺必填属性的实例 → 发布前门禁报违规并阻断；补上后放行。

**代价**：2–3 天。

## P3 · 统一「证据」概念：规则解释 + 决策留痕

现在 `ConditionResult`（规则输出）和 `AgentTrace`（执行留痕）是两套。先合并语义再补功能，避免各做各的。

**做法（分两步，别一次做完）**

1. **渲染层**：给 `rule_engine.py` 的结果加 `explain()`，输出"命中规则 X；条件 A=1.2 满足（阈值 ≥1.0）；数据取自 Y 表，读取时间 Z"。前端在规则测试沙箱和行动执行结果处展示。
2. **留痕层**：新增 `backend/app/models/evidence.py`，字段建议 `id / subject_type / subject_id / conclusion / rule_id / inputs(JSON) / data_snapshot_time / created_at`，把规则结论和 Agent 决策都写进这一张表。`AgentTrace` 保持不动（它记过程），新表记依据。

**涉及文件**：`services/rule_engine.py`、`services/function_executor.py`、`models/trace.py`（参考）、新增 `models/evidence.py`、`api/v1/traces.py`（新增查询接口）、前端规则/智能体详情

**验收**：任一规则结论可通过接口反查到"哪条规则 + 哪些输入值 + 数据时间"。

**代价**：第一步 1 天；第二步 2–3 天。

## P4 · 溯源与完整性（先接线，再上哈希链）

Semantica 的教训就在这条：**设计好了但没接默认路径**。所以我们反着做 —— 先接线，后加锁。

1. 先让每次写入本体的操作都记录来源（谁、什么时间、依据哪份文档/哪条资产映射/哪次 AI 抽取）。数据模型用 PROV-O 的 entity/activity/agent 三元思路，不必照搬类名。
2. 记录稳定后，再加哈希链（`verify_chain()`：逐条 `sha256(prev_hash || entry)`）做篡改检测，以及墓碑式作废（不物理删，写一条 invalidate 记录）。
3. **图上要标可信度。** 它的 `/api/provenance` 返回里带 `source: "audit" | "graph_traversal"` 和 `integrity_verified`：审计库为空或 checksum 对不上时，自动降级成"从知识图谱 ego_graph 半径 2 遍历出来的近似图"。降级本身是对的（总比空图有用），**错的是前端两种来源长得一模一样**。我们做血缘视图时必须把 `source` 显示成不同样式。
4. 用 `scripts/customer_demo.py` 的演示路径验证链路真实被写入 —— **别只在测试里看到它**（Semantica 就是反面教材：14 个 `*_provenance.py` 包装器里只有 `kg_provenance.py` 被真实 import）。

**涉及文件**：新增 `services/provenance.py` + `models/provenance.py`、`services/ontology_mapping_service.py` 与 `doc_builder.py`（写入点）、`api/v1/governance.py`（查询）

**代价**：第 1 步 2 天；第 2、3 步各 1–2 天，可延后。

## P5 · 低成本顺手项（各半天以内，可穿插做）

| 项 | 做法 | 涉及文件 |
|---|---|---|
| **文档链接门禁** | 写 `scripts/docs_check.py` 扫 `docs/**.md` 与 `README*.md` 的相对链接，不存在即退出非零；挂进 P0 的 test stage | 新增脚本；`docs/`（README 里已删掉两张本机绝对路径图片，正是这类问题） |
| **评测三态** | `EvalResult` 加 `status ∈ {stable_pass, flaky, stable_fail}`，同一 case 连续两次结果不同自动标 flaky | `models/eval.py`、`api/v1/evals.py` |
| **默认拒绝启动** | 关键环境变量（`SECRET_KEY`、模型 key）未配置时服务拒绝启动，而不是用弱默认值起来 | `backend/app/main.py`、`scripts/deploy/deploy-docker.sh`（注意别打断现有 `BOOTSTRAP_ADMIN_PASSWORD` 回落逻辑） |
| **文档意图路由表** | 新增 `docs/choose-your-module.md`："我想接入一张表 → …；我想让 AI 抽本体 → …；我想上线一个场景 → …" | 新增 `docs/` 文件 |
| **连接器改两级注册** | 现在是「DB 类用 `@register` 装饰器 + 非 DB 类手写塞 `_by_kt` 字典」两套混用。统一成 `(category, type)` 双键装饰器，`list_supported()` 直接喂前端建表 | `app/connectors/__init__.py` |
| **SSRF 防护** | 读外部 URL / REST API 前先 DNS 解析再判内网地址，重定向时按需剥离 Authorization —— `api` 类连接器目前没这层 | `app/connectors/http_api.py`，参考 `semantica/ingest/ssrf.py` 的 `_ip_is_blocked` / `_should_strip_auth` |
| **敏感内容预筛不留原文** | 扫描器只产出 finding（类型+位置），**故意不抄原文摘录**，避免把密钥复制进报告或血缘记录 | 新增 `services/data_plane/screening.py`，参考 `ingest/screening.py` |
| **第三方 Action 按 SHA 固定** | `.github/workflows/*` 里 `uses:` 全部改成 `owner/repo@sha` 并加注释保留可读版本 | `.github/workflows/deploy.yml` |

## 明确不做

- **OWL DL / HermiT / Pellet 级一致性推理** —— 上游是占位实现，我们 README 已把口径降为"RDF/OWL 文件导入导出"，保持不动。
- **23 种解析器 / 8 家 LLM Provider 适配** —— 与我们的连接器框架定位重叠，投入无回报。
- **手写 MCP Server** —— Semantica 这套无鉴权、整份 JSON 读写磁盘，不如用官方 SDK。
- **实体三层去重 + 六策略裁决** —— 等高合规客户真的提出"同一客户三个名字"再做，现在做属于自我感动。
- **7 种平台的 `deploy/` 目录、3 OS × 4 Python 的安装矩阵** —— 我们只有一套 ECS + docker-compose，抄过来是维护负担。

## 建议的第一周

P0（CI 止血）+ P5 的文档链接门禁和意图路由表，再加 P1 的数据结构设计。理由：P0 独立于业务改动、能立刻降低后续所有改造的风险；P1 只加字段不动逻辑，可以先把"出处"这个概念铺进 schema，真正的回指校验放到第二周。
