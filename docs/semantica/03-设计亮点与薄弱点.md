# 03 · 设计亮点与薄弱点

这一篇解决两个问题：**哪些设计值得抄**，**哪些地方它的实现配不上它的宣传**（避免我们照着 README 立目标）。

## A. 五个真正漂亮的设计

### A1. draft → approve → schema gating

抽取出来的东西先进草案区，审批通过后才由 `filter_by_schema` 过滤并写入主图。价值不在于"有审批"，而在于**主图永远只有一份被确认过的语义**，AI 的错误不会污染下游查询。

知彼已经有建模草案（`backend/app/models/modeling_draft.py`）和发布流水线（`api/v1/ontology_publish.py`），但两者是**分开的两段**：草案管的是编辑期，发布管的是版本上线。中间缺的正是"AI 产出 → 通过 schema 校验 → 才能进草案"这一道门。

### A2. `_find_span_in_text`：抽取结果必须能回指原文

任何抽出来的实体/关系，都要在原文里找到支撑片段；找不到就丢弃。这一条把 LLM 幻觉从"事后人工发现"变成"入库前自动拦截"，实现成本大约几十行。

对我们尤其合适：知彼有 `services/doc_builder.py`（文档抽取，SSE 流式）和 `services/ai_builder_v2.py`，抽取结果直接进 `ontology_constraints.py` 做**格式**校验，但没有**出处**校验。加上回指检查后，前端实体详情可以直接展示"这条关系来自第 3 页第 2 段"，客户演示时的说服力完全不是一个量级。

### A3. `InferenceResult` + `ExplanationGenerator`：结论自带推理路径

规则命中不是返回一个 bool，而是返回结构化对象（哪条规则、代入哪些值、什么时间），再由 `ExplanationGenerator` 渲染成人话。这是把"AI 说了算"变成"AI 可以说清楚"的关键一步。

知彼 `services/rule_engine.py` 里的 `ConditionResult` 已经是结构化起点（有 field、display），离这一步只差"把整条规则链拼起来并生成可读解释"。

### A4. `FactSupport` 真值维护（TMS）

每条派生事实记录它依赖的前提集合；前提被撤销或修订时，依赖它的派生结论自动失效。这解决了知识图谱最常见的腐坏方式：**源头改了，推导结果还留在图里当真**。

这块我们没有对应物，而且它会随数据量增长变成事故源。优先级排在 A2/A3 之后，但方向上必须补。

### A5. 工程纪律类设计（成本极低、回报极高）

这几条不需要动产品代码，今天就能加：

| 设计 | 一句话说明它为什么值 |
|---|---|
| **已知失败债务台账** | CI 允许有失败，但清单只减不增，新增即红、修掉必删。把"测试不稳定"从借口变成待办 |
| **`docs_check.py` 链接门** | 文档里的相对链接不存在就报错。知彼 `docs/` 已有近 10 个文件，README 刚清掉两张失效的本地绝对路径图片，正是这类问题 |
| **Action 按 SHA 固定 + 校验 job** | 供应链防护，防的是第三方 action 被打标记入投毒 |
| **被忽略的 CVE 必须写可达性论证** | 强制区分"确认不受影响"和"懒得看" |
| **`choose-your-module.md` 意图路由表** | 用"我想做什么"索引文档，不是用模块名 |

## B. 薄弱点：宣传与实现的差距

| 宣传口径 | 实际实现 | 判据 |
|---|---|---|
| OWL DL 一致性推理（HermiT/Pellet 级） | 启发式检查 | `ontology_validator.py:336-353` 明确是占位 |
| 端到端溯源 | 溯源管理器**未接入默认管线**。每个模块都配了一个 `*_provenance.py` 包装器（ingest/parse/normalize/semantic_extract/dedup/conflicts/embeddings/export/graph_store/kg/llms/ontology/context/pipeline 共 14 个），但全库检索后**只有 `kg/kg_provenance.py` 被真实 import**（`kg/__init__.py`、`kg/node_embeddings.py`）；其余 13 个是孤儿模块。`ProvenanceManager()` 的实际调用点只有 `cli.py` 与 `explorer/session.py`（外加 `context/decision_recorder.py`） |
| 因果推理 | 决策图遍历 | — |
| 多级审批编排 | `ApprovalChain` 只是单条审批流水记录 | — |
| 多语言图存储对等 | LPG（内存 networkx 风格）是主，RDF 三/四元组存储是导出与 SPARQL 旁路 | `kg/knowledge_graph.py`、`context/context_graph.py` |
| 双 MCP 实现 | 包内一套 + `semantica_mcp` 一套，后者**无鉴权**且整份 JSON 全量读写磁盘 | `semantica_mcp/mcp/server.py` |
| 覆盖率保障 | 有 482 个测试文件，但**没有覆盖率门槛** | CI 配置 |
| 版本口径 | `SECURITY.md` 与 `__version__` 不一致 | — |

**结论：不要因为看到"OWL DL"“HermiT”就推翻现有架构。** 上游自己都没做到，我们README 里已经改成如实描述能力边界（本次已把 OWL 2 对齐的措辞降为"RDF/OWL 文件导入导出"），这个口径是对的。

## C. 从薄弱点里反推出的三条自检规则

抄任何"看起来很好的功能"之前，先问三个问题：

1. **它在默认路径上被调用吗？** —— 去 `cli.py`、`server.py`、主编排函数里找调用点，只在测试里出现的功能等于没做。
2. **它的数据结构接到了存储层吗？** —— 有 `ProvenanceEntry` 类但默认不写库，就是装饰品。
3. **它的宣传词有对应测试吗？** —— 482 个测试文件仍然没覆盖 OWL DL 承诺，说明"有测试"不等于"承诺被验证过"。

这三条同样适用于自查知彼：比如 `models/trace.py` 的 `AgentTrace` 是否真的在所有场景路径上写入了？`models/eval.py` 的评测有没有接进 CI？（见 [04-对照知彼的差距.md](04-对照知彼的差距.md)）
