# 生产环境操作与自测说明

适用于部署在 `http://182.92.185.115:8088` 的 Ontology 系统。先看页面右上角的产品版本、构建时间和提交标识，确认浏览器加载的是最新部署。产品版本统一读取仓库根目录 `VERSION`；每次正式发布至少递增补丁版本。以下测试从只读检查开始；“运行真实管道”会写入目标表，请在演示数据项目中操作。

## 一、五个“数据集成”菜单分别做什么

| 菜单 | 作用 | 自测时看什么 |
| --- | --- | --- |
| [数据接入](http://182.92.185.115:8088/data/connections) | 保存数据库等数据源的地址和访问配置，并测试是否能连接。建立连接本身不会同步业务数据。 | 找到演示数据源，检查状态与连接测试结果。 |
| [资产目录](http://182.92.185.115:8088/data/assets) | 登记和查看接入源中的表、字段等元数据，供项目选用。看到资产不代表管道已经跑过。 | 找到该场景的源表和输出表，查看字段。 |
| [数据管道](http://182.92.185.115:8088/data/pipeline) | 按配置从源查询读取数据、做列映射或转换、写入目标表，相当于一条 ETL 作业；可用于同步/加工，但不是自动持续同步。 | 选择“真实 ETL”的管道，先点“预览”，核对来源、目标和样本；运行后查看读取/写入行数及状态。“演示”引擎只播放进度，不搬运数据。 |
| [数据血缘](http://182.92.185.115:8088/data/lineage) | 回答“这个本体对象用了哪项数据资产、哪些业务动作读了它”。例如 `订单表 → 订单本体 → 库存风险动作`。 | 点击节点看来源和关联边。当前覆盖资产、本体类型、业务动作；尚不等于所有 ETL 步骤和外部系统的完整端到端血缘。 |
| [数据质量](http://182.92.185.115:8088/data/quality) | 对已有本体数据资产做健康度检查，展示分数、告警和趋势。 | 点“立即检测”，检查实体健康度和具体问题。没有已绑定资产时会显示空态。 |

“血缘”就是数据的来路和去向。若订单本体中的“金额”不对，可以沿血缘回看它来自哪张资产表；若源表调整，也可看哪些本体或动作可能受影响。

## 二、按六步业务链自测（建议用合成供应链项目）

1. 打开[业务交付工作区](http://182.92.185.115:8088/workspace/projects)，选择已有的“电商供应链”演示项目。若不存在，管理员展开“非军事验收样例”后创建；创建会新增演示数据和项目记录。
2. **需求分析**：阅读项目目标和验收条件，确认要回答的业务问题，例如库存或物流风险。
3. **数据源表**：在“数据接入”和“资产目录”找到该项目选用的数据源和表，确认连接、表名、字段。
4. **数据处理**：在“数据管道”找项目关联的“真实 ETL”管道，先“预览”。若需要验证重新加工，再回项目点击“保存并运行项目管道”；该操作会写目标表。核对最近一次运行成功及读取、写入行数。
5. **子图建模／本体库**：在项目查看对象映射和发布版本；进入[图谱探索](http://182.92.185.115:8088/studio)选择该场景，点对象和关系，检查属性与实例。也可在“数据血缘”看资产到对象的映射。
6. **本体应用**：打开该项目已发布的运行页，按页面提供的参数试运行；在[技能管理](http://182.92.185.115:8088/agent/toolbox)查看已发布技能和执行记录；最后打开该项目智能体的“对话测试”，询问“当前哪些订单存在库存或物流风险？”。答复应有技能调用证据、数据库结果和执行编号。若提示需要人工复核，应到应用运行页处理，聊天本身不会写业务数据。

只读快速检查可以直接做步骤 1、2、3、5、6；步骤 4 的真实运行会更新演示目标表。

## 三、确认这次到底调用了哪个大模型

1. 管理员打开[系统配置](http://182.92.185.115:8088/ops/config)的“AI 配置”，找到 DeepSeek 卡片，检查 **模型 ID**、Base URL、使用场景，点击“测试连通性”。模型名称可以是自定义显示名；真正发送给服务商的是“模型 ID”。Base URL 使用官方 OpenAI 兼容地址 `https://api.deepseek.com`，模型 ID 必须是 DeepSeek 官方当前支持的准确值。常见官方示例为 `deepseek-chat` 或 `deepseek-reasoner`；不要仅凭“V4-Flash”这样的展示名称推定 API ID 为 `deepseek-flash`。以 [DeepSeek 官方 API 文档](https://api-docs.deepseek.com/zh-cn/)和账户实际开放模型为准。
2. 打开[智能体管理](http://182.92.185.115:8088/agent/manage)，选择要测试的智能体。左侧“业务技能”下方的“使用模型”显示当前配置解析出的模型。若该智能体明确绑定了模型管理中的模型，它优先于系统配置的通用/场景模型；演示助手在没有显式绑定时会选一个已配置的 DeepSeek 模型，不能仅凭模型卡片名称判断它必然选中了 Flash。
3. 发送问题后，在答复上方看“**本次调用模型：...**”，这是后端发出的本次请求模型 ID；下方技能证据显示工具是否成功。模型连接测试只验证一次最小问答，不能证明工具调用也成功；完整闭环需要“模型答复 + 成功的技能证据 + 数据结果”。
4. 如需排查，在浏览器开发者工具的 Network 中打开 `/api/v1/agents/.../chat`，查看 **Response**（响应正文）。它是 `text/event-stream`：`model_status` 给出模型 ID，`tool_result` 给出技能结果，`answer` 才表示完成；`error` 表示调用失败。HTTP `200 OK` 只表示流已建立，不代表模型或技能成功。

若显示 401，优先在系统配置里重新输入密钥、保存后用“测试连通性”验证，同时核对 Base URL 与密钥是否属于同一 DeepSeek 服务。若显示 404，核对模型 ID 和接口地址；429 则检查额度或请求频率。不要把完整 API Key、浏览器 Authorization 头、服务器环境变量或原始请求报文发给别人。此前在聊天中暴露过的密钥应在 DeepSeek 控制台撤销并换新。

## 四、如何判断整条链通过

检查项目的真实管道运行记录、发布应用的试运行结果、技能的数据库执行记录，以及智能体本次响应中的 `model_status → tool_result(success=true) → answer`。四项都通过，才说明“数据 → 本体 → 技能 → 大模型答复”在该演示场景跑通。GitHub Actions 部署显示成功只证明当次启用的检查通过；服务器未设置 `CHECK_AI=1` 时，部署流程不会执行真实 DeepSeek 问答验收。

如果浏览器报错但 Network 状态是 200，请复制 **Response 中的事件类型、错误文字和模型 ID**（删掉任何密钥/令牌）；这比只提供 200 状态更能定位问题。
