# 本体项目数据血缘模块改造方案

版本：V1.0｜2026-10-15

## 1. 设计目标与依据

本次改造的目标是：**名称看得懂、数据路径连得上、关系依据查得到。** 用户无需理解英文枚举或图数据库，就能回答：数据从哪里来、用到了哪里、发生变更可能影响什么。

本方案依据用户提供的《数据血缘页面改造方案》。目前未取得项目源码、原型 HTML、展示截图及 Semantica 实际页面，原方案中的代码诊断尚待核实。本文提供独立的展示设计和实施建议，借鉴 Semantica 图谱工作台的设计方向，不声称复刻其实际界面。下文业务名称、数量和时间均为示例。

首版优先完成中文化、节点聚焦、上下游追踪、路径阅读和关系详情。全图作为辅助入口，不作为默认主视图。

## 2. 页面展示设计

### 2.1 整体布局

采用顶部工具栏、左侧节点导航、中央关系画布、右侧详情面板。视觉采用深色图谱工作台风格，保持本项目既有组件和字体习惯。

```text
┌────────────────────────────────────────────────────────────────────────────┐
│ 数据血缘   [搜索数据表、业务对象、行动或规则……]            [导出] [帮助]    │
├────────────────────────────────────────────────────────────────────────────┤
│ 当前：客户对象   [查来源] [查影响] [来源与去向]   展开层数 [1层 ▾]          │
│ 关系 [全部 ▾]    依据 [全部 ▾]             已显示 8 个节点 · 9 条关系       │
├────────────┬──────────────────────────────────────────┬────────────────────┤
│ 节点导航   │ 2 条绑定待复核                    [定位] │ 客户对象           │
│            │                                          │ 业务对象 · 客户域  │
│ 数据资产   │      来源          当前         使用方   │                    │
│ 业务对象   │                                          │ [概况] [关系依据]  │
│ 业务行动   │ ┌────────┐    ┌────────┐    ┌────────┐   │                    │
│ 业务规则   │ │客户主表│───→│客户对象│───→│客户查询│   │ 来自哪里           │
│            │ │客户库  │映射│ 已选中 │读取│业务行动│   │ 客户主表 · 字段映射│
│ 最近查看   │ └────────┘    └────────┘    └────────┘   │                    │
│ ·客户对象  │                    │                     │ 用到哪里           │
│ ·保单主表  │                    └────→┌────────────┐  │ 客户查询 · 被读取  │
│            │                     校验 │资料完整性规则│  │ 完整性规则 · 校验  │
│            │                          └────────────┘  │                    │
│            │ [－][100%][＋][适应画布]       [图例 ▴]  │ [查看业务对象]     │
├────────────┴──────────────────────────────────────────┴────────────────────┤
│ 当前路径：客户主表 → 字段映射 → 客户对象 → 被读取 → 客户查询               │
└────────────────────────────────────────────────────────────────────────────┘
```

图中“读取”“校验”为紧凑示意，实际连线使用下文统一的中文文案。右侧详情和左侧导航可折叠，给画布更多空间；窄屏将详情改为抽屉。

### 2.2 默认进入方式

- 从某个资产或对象进入：直接聚焦该节点，默认展示一层“来源与去向”。
- 从菜单进入：展示搜索、最近查看和分类列表，提示“选择一个节点，查看数据来源和使用去向”。
- 用户主动选择“全局概览”才加载受限全图。大图先按业务域或类型筛选。
- 无关系时显示“暂未发现关联关系”，并说明已检查配置、执行记录中的哪些来源。
- 权限不足、加载失败、确实没有关系分别展示，不能都显示为空图。

## 3. 中文表达规范

### 3.1 术语对照

| 技术概念 | 页面文案 | 说明 |
|---|---|---|
| asset | 数据资产 | 卡片进一步显示数据表、文件等类型 |
| object_type | 业务对象 | 如客户对象、保单对象 |
| action | 业务行动 | 如客户查询、保单同步 |
| rule | 业务规则 | 如资料完整性校验 |
| upstream | 查来源／来自哪里 | 避免要求用户理解“上游” |
| downstream | 查影响／用到哪里 | 按用户当前任务使用 |
| depth | 展开层数 | “1层：只看直接关联” |
| inspector | 详情 | 不直接显示英文标题 |
| needs_review | 待复核 | 同时解释触发原因 |
| deprecated | 已停用 | 不与无执行记录混用 |
| configuration | 配置依据 | 来自绑定、规则或任务定义 |
| execution | 执行记录 | 来自某次实际运行 |
| inference | 推导关系 | 提供规则与支撑路径 |

名称优先级：业务别名 → 中文名称 → 原始名称 → “未命名数据表”等兜底名称。UUID 只在技术信息中展示并提供复制，不能作为节点主标题。

原始表名、英文属性名可以作为辅助信息，帮助技术人员核对；不强行翻译数据库标识，也不让它们主导页面。

### 3.2 节点卡片

```text
┌─ 数据表 ─────────────────┐     ┌─ 业务对象 ───────────────┐
│ 客户主表                 │     │ 客户对象                 │
│ 客户数据库 · 生产环境     │     │ 客户域 · 核心层           │
│ customer_master          │     │ 12 个属性                │
└──────────────────────────┘     └──────────────────────────┘
```

- 业务名称为视觉主体，类型和所属系统为辅助信息。
- 名称最多两行，完整名称可在点击详情、键盘聚焦或悬停时查看。
- 同名节点必须通过系统、环境或业务域区分。
- 徽章只显示重要状态，例如“待复核”“已停用”。
- T1/T2/T3 只有在项目已有明确中文定义时才显示中文层级标签，不能自行解释为核心层等含义。

### 3.3 关系读成一句话

| 关系事实 | 画布数据流方向 | 连线文字 | 详情解释 |
|---|---|---|---|
| 客户表向客户对象供数 | 客户表 → 客户对象 | 字段映射 | 客户对象通过字段映射使用客户主表的数据。 |
| 客户查询读取客户对象 | 客户对象 → 客户查询 | 被读取 | 客户查询读取客户对象的数据。 |
| 保单同步写入保单表 | 保单同步 → 保单表 | 写入 | 保单同步将处理结果写入保单主表。 |
| 汇总表来源于明细表 | 明细表 → 汇总表 | 加工生成 | 明细表经过加工生成汇总表。 |
| 规则使用客户对象校验 | 客户对象 → 完整性规则 | 用于校验 | 完整性规则使用客户对象的数据执行校验。 |

上述文案必须根据真实语义映射。绑定若仅为元数据关联，应显示“关联配置”，不自动参与数据流和影响传播。

## 4. 视觉与布局规范

### 4.1 按数据路径分层

主阅读方向统一为：**来源 → 当前节点 → 使用方**。

不把资产、对象、行动、规则固定成四条不可变泳道。行动可能回写资产，资产也可能派生其他资产，固定类型顺序会造成反向连线和误读。

- 根据相对当前节点的路径层级布局，同层按类型和业务域分组。
- 节点类型用中文类型、图标和左侧色条共同表达。
- 默认一层，可选一至五层，支持逐节点展开。
- 展开时尽量固定当前节点位置，避免整个画布跳动。
- 回写使用折返线，循环依赖显示提示；后端遍历必须防环。
- 高连接度节点显示“还有 26 个使用方”，按需加载。
- 初始建议上限为 80 个节点、150 条关系，实际以性能测试调整。超过上限明确提示“当前仅展示部分结果”，提供筛选或继续展开入口。
- 评估 ELK 等分层布局能力，结合现有 VueFlow 版本确定选型。

### 4.2 工作台风格建议

以下为建议值，不是对 Semantica 的实测参数。

| 元素 | 建议 |
|---|---|
| 画布 | 深蓝黑 `#0B1220`，低对比点阵，可关闭 |
| 面板 | `#111C2E`，边框 `#34445D` |
| 主文字／次文字 | `#F1F5F9`／`#A8B6CC`，实现后检查对比度 |
| 选中强调 | 青蓝 `#38BDF8`，同时显示选中状态文字 |
| 类型颜色 | 资产蓝、对象青、行动紫、规则琥珀色 |
| 节点尺寸 | 宽约 220px，最小高约 96px，长名称可增高 |
| 连线 | 默认 1.5px，选中路径 2.5px |
| 字号 | 业务名称 14px，辅助信息不小于 12px |
| 面板宽度 | 左侧约 220px，右侧约 340px，可折叠 |

项目已有主题体系时，应同步适配，深色不应成为唯一可读的主题。

### 4.3 一种视觉提示表达一种含义

- 颜色表示节点类型，中文类型和图标提供冗余识别。
- 箭头表示数据流方向。
- 实线表示有直接依据的关系，虚线表示按规则推导的关系。
- 中文边标签表示关系类型，不再为 reads、writes 叠加多套线型。
- “待复核”“已停用”用文字徽章表达。
- 调用次数、最近执行时间放详情，首版不控制线宽。
- 选中路径提高亮度；其他关系降低强调但保持可读。

右下角提供常驻可折叠图例。零次执行不表示废弃，也不自动变灰。

## 5. 关键交互及展示效果

### 5.1 查来源

操作：搜索“客户对象” → 点击“查来源” → 选择“客户主表”。

画布高亮相关关系，底部显示：

> 客户主表 → 字段映射 → 客户对象

右侧显示完整解释与配置依据。若已有字段级数据，展示：

| 来源字段 | 对象属性 | 处理方式 |
|---|---|---|
| 手机号码（mobile_no） | 联系电话 | 直接映射 |
| 客户编号（customer_id） | 客户标识 | 类型转换 |

如果当前只有表级关系，显示“目前仅记录到表级关系，暂无字段映射明细”，不能生成不存在的字段血缘。

### 5.2 查影响

操作：选择“客户主表” → 点击“查影响”。

摘要示例：

> 当前查询范围内，发现 1 个直接依赖对象、3 个间接使用方；2 条关系待复核。

右侧按“直接依赖”“间接使用”分组，逐项提供“查看路径”。计数按节点去重，注明当前层数、筛选条件及结果是否截断。

查影响表示潜在依赖影响，不表示一定发生故障。详情给出具体理由，例如“该对象绑定了此表，修改已映射字段可能导致绑定失效”。

### 5.3 阅读完整路径

选择一个间接使用方后，高亮完整路径，而非只高亮起终点：

> 客户主表 → 字段映射 → 客户对象 → 被读取 → 客户查询

路径面包屑中的节点可以点击。多路径时默认展示最短路径，显示“另有 3 条路径”，允许切换或仅看当前路径。

### 5.4 节点详情与关系详情分开

选节点：显示名称、类型、所属系统、状态、“来自哪里”“用到哪里”和业务页面入口。

选连线：显示关系说明、配置依据、执行情况、状态、复核原因和相关操作。

```text
关系详情
客户主表 → 客户对象
字段映射                              待复核

关系说明
客户对象通过配置绑定使用客户主表的数据。

配置依据
绑定名称：客户基础信息映射
最近修改：2026-10-12 14:30
[查看绑定配置]

执行情况
当前查询时间范围内，暂无关联执行记录。

复核原因
来源表结构发生变化，请检查已映射字段。
[查看变更] [前往复核]
```

只有存在相应能力且用户有权限时才显示按钮。证据缺失显示“依据详情暂不可用”。无执行记录不等于配置失效。

## 6. 来源、状态与可信度设计

### 6.1 分开表达四个维度

| 维度 | 建议取值 | 含义 |
|---|---|---|
| 依据来源 | 配置、执行、推导、待确认 | 为什么认为存在该关系 |
| 有效状态 | 有效、已停用、未知 | 关系是否仍生效 |
| 复核状态 | 无需复核、待复核 | 变更后是否需要确认 |
| 校验状态 | 未检查、通过、失败、不适用 | 执行了什么校验及结果 |

同一关系可同时具备配置和执行证据。优先在关系及证据上标注来源，不把一个节点整体标为“审计级”。筛选文案采用“仅含执行记录”“包含配置依据”等可理解表达。

历史来源不明的数据标为“待确认”，不能统一默认填为 audit 或校验通过。

### 6.2 推导关系准入条件

1. 只沿明确允许的依赖类型遍历，并定义方向和组合规则。
2. 返回支撑结论的原始关系与路径。
3. 说明推导规则、层数和查询范围。
4. 推导结果不得因反复查询而自动升级为直接证据。

多跳路径本身可以展示，无须伪造新的直接关系。若折叠成汇总线，标为“经 2 层依赖”，可展开。

没有执行记录时展示已有配置依据，不使用任意知识图谱邻居来填充空图。仅为展示生成的推导关系优先放响应层，是否改数据库取决于实际持久化需求。

### 6.3 关系检查横幅

分类展示：引用对象不存在、关联资产已停用、结构变更后待复核、记录校验失败（仅在已有校验机制时）。

每项包含原因、数量、检查时间和定位入口。只检查当前视图时，不得声称全系统无异常。引用一致性检查与审计链验证分别命名。校验失败后展示其他来源，也必须保留失败提示。

## 7. 前后端实施建议

### 7.1 先建立关系语义表

为每种关系定义原始端点、数据流向、中文正反向文案、是否参与影响传播、允许的证据来源。

特别核对：reads 可能存储为“行动 → 对象”，数据流却是“对象 → 行动”；derives_from 可能存储为“产物 → 来源”，数据流却相反。不能直接把数据库所有出边当作下游。

绑定语义、规则语义和写入语义必须结合实际代码确认。布局、遍历和路径解释使用同一套规则。

### 7.2 建议接口能力

| 能力 | 要求 |
|---|---|
| 节点搜索 | 支持中文名、别名、原始名，结果含类型、环境，分页返回 |
| 上下游追踪 | 节点、方向、层数、关系类型、证据类型、范围限制 |
| 增量展开 | 保留现有画布，节点与边去重 |
| 关系详情 | 返回配置引用、执行引用及推导支撑路径 |
| 关系检查 | 返回类别、范围、时间、定位信息 |
| 导出 | 保留查询条件、覆盖范围和截断说明 |

可复用现有接口，不强制新建 POST /lineage/trace。接口形式应符合项目习惯，重点在语义一致。

筛选会改变路径或影响计数时由后端重新查询；只隐藏当前画布元素才属于纯前端过滤。两者在界面区分为“查询条件”和“显示设置”。

### 7.3 建议字段契约

| 对象 | 建议字段 | 说明 |
|---|---|---|
| 节点 | id、kind、label、sub_label、status、needs_review | ID 需避免跨类型冲突 |
| 关系 | id、flow_from、flow_to、relation、label | 明确数据流向，兼容原始端点字段 |
| 关系依据 | evidence_types、evidence_refs | 可有多种依据，详情按需加载 |
| 关系状态 | status、needs_review、review_reason | 与执行次数独立 |
| 推导信息 | supporting_edge_ids、path、rule | 可还原解释 |
| 查询信息 | direction、depth、filters、time_range | 便于复现与导出 |
| 覆盖信息 | truncated、checked_sources、unavailable_sources、generated_at | 区分无结果与未完整查询 |

每条返回关系的端点必须在当前可见结果中存在，或明确采用授权的边界节点策略。权限限制不得通过路径、数量或证据详情泄露未授权信息。

weight 若表示调用次数，必须说明窗口，例如“最近 7 天执行 23 次”；没有明确统计定义时暂不展示。后端必须处理防环、超时、节点上限和部分来源失败。

## 8. 导出设计

提供“当前视图 JSON”和“中文 Markdown 报告”。报告包含：当前节点、方向、层数、筛选与时间范围、生成时间、直接及间接依赖摘要、中文路径清单、关系依据与状态、待复核问题、是否截断及来源不可用说明。

标题示例：“客户对象数据血缘报告”。未满足正式审计要求前，不称为审计报告。导出沿用访问权限；大范围导出另行评估服务端任务。

## 9. 实施顺序与交付物

| 阶段 | 改造内容 | 交付物 |
|---|---|---|
| 一：读得懂 | 中文节点、关系文案、方向核实、卡片、详情、图例、工作台样式 | 可阅读的现有关系图、中文文案表、关系语义表 |
| 二：连得上 | 搜索、上下游、层数、增量展开、分层布局、完整路径、回路与截断处理 | 围绕节点完成来源与影响查询 |
| 三：有依据 | 配置/执行/推导区分、关系证据、检查提示、历史来源确认 | 带依据和覆盖说明的血缘查询 |
| 四：可分享 | 中文报告、JSON、字段级能力接入、性能与无障碍优化 | 导出报告、性能验证结果 |

字段级溯源只接入已有能力；若尚未建设，需要单独估算，不作为页面改造顺带完成的事项。工期应在核实代码、数据量、执行记录与历史迁移成本后确定。

## 10. 验收标准

### 可读性

- 首屏不以英文枚举或 UUID 充当业务标题。
- 每条可见关系有中文解释，箭头与解释一致。
- 选中使用方后能看见完整依赖路径。
- 同名、长名称、空结果、失败和权限状态均可理解。

### 正确性

- 用“表 → 对象 → 读取行动”“行动 → 写入表”分别验证方向。
- 用派生关系、循环和多路径验证查询结果。
- 零次执行不变成废弃，配置无执行记录仍可显示。
- 来源、有效状态、复核和校验分别表达。
- 截断、权限范围与部分失败不伪装成完整结果。
- 影响数量按节点去重，筛选口径与画布一致。

### 展示与性能

- 以约 10、50、80 个节点样例检查遮挡、可读性、布局与交互，最终阈值按测试调整。
- 提示可定位问题关系，影响结果可直接查看路径。
- 颜色之外还有文字、图标或线型提示。
- 导出条件与当前查询一致，包含覆盖范围。

### 用户验证

邀请至少 3 位熟悉业务但不熟悉技术字段的用户完成：找到客户对象来源、找到客户主表变更的潜在影响、解释一条待复核关系。记录完成情况、耗时、英文理解障碍和箭头误读，据此调整默认展示与文案。

## 11. 开发前核实清单

1. 各 relation 的真实端点方向、产生位置与更新机制。
2. weight 的含义、统计窗口及现有失效状态。
3. 配置、执行、字段映射分别能提供什么证据。
4. 实际节点量、边量、最大连接度与查询延迟。
5. VueFlow、布局库和详情组件版本。
6. 中文别名覆盖率及同名资产的系统、环境字段。
7. 节点、关系、证据和导出的权限规则。
8. Semantica 实际页面或截图，用于进一步校准视觉细节。

最终优先级：**先让关系读得懂，再让路径查得准，随后补足依据与报告。**
